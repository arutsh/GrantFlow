Code review (not pytest — none of these have DB/route-level test coverage that would catch a blocked event loop) surfaced three more real regressions, all the same shape: a route/service that was plain `def` before (FastAPI auto-threadpools those) became `async def` here, but a blocking call inside it stayed synchronous — now blocking the event loop directly instead of running off-thread. Existing `patch("...verify_password", return_value=True)`-style test mocks auto-upgraded to `AsyncMock` with no test changes needed (Python's `unittest.mock.patch` auto-detects a coroutine-function target). Also found: `user_routes.py`'s `update_user_endpoint` returned a stale `db_user.customer` after the founder-promotion flow — `expire_on_commit=True` (the old sync default) used to force a refetch on next access, `expire_on_commit=False` (required for async) doesn't, so the endpoint now explicitly does `db_user.customer = customer` after the update to keep the in-memory relationship in sync with the new `customer_id`.
