**Concurrency fix (2026-07-26):** FIFO allocation's read-then-write (`list_unconsumed_lots`/`list_unsatisfied_report_lines` followed by `create_allocation`) had no locking, so two concurrent requests against the same budget could both read the same lot balance and double-spend it — flagged in the code review above, deferred pending a read-up on locking options. Resolved with `budget_ledger_lock(db, budget_id)` in `currency_ledger_services.py`: a **session-level** Postgres advisory lock (`pg_advisory_lock`/`pg_advisory_unlock`, not the transaction-scoped `_xact_` variant) acquired on a dedicated connection checked out directly from the engine pool, wrapping `record_conversion_service`, `create_report_line_service`, and `update_report_line_service`. Session-level and on a separate connection specifically because every crud call in this codebase commits immediately — a lock tied to `db`'s own transaction, or to whatever connection `db` happens to hold at a given instant, would be released or silently migrate to a different connection the moment the first nested crud call commits. Serializes only same-budget ledger writes; different budgets stay fully parallel. No-ops outside Postgres (the sqlite-backed unit suite). Verified with `services/budget/tests/test_budget_ledger_lock.py` against real local Postgres (skips gracefully if unreachable, same convention as `test_storage_service.py`/MinIO): proves a second, independent connection is actually blocked from acquiring the same budget's lock while held, is unaffected by a different budget's lock, and that the lock keys identically regardless of whether `budget_id` arrives as `str` or `uuid.UUID` (GUID's type decorator returns different Python types per dialect — see `shared/db/type_decorators.py`).
