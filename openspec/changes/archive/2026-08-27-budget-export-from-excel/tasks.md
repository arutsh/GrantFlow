- [x] 5.4 In budget's `create_budget_with_lines_service`: fall back to the organization's own default currency (`customer.currency`, via `get_customer_cached`) when the request's `local_currency` is unset, instead of the current hardcoded model default. In chat's `import_excel.py`: apply the existing 0.6 confidence threshold to `local_currency_confidence` (pass through unset rather than a low-confidence guess), set `actual_currency`/`donor_total_amount`/`duration_months` directly from the extraction, and compute `estimated_exchange_rate` as `sum(line amounts) / donor_total_amount` (guarding zero/None)
- [x] 5.5 Add tests: dual-currency sheet extracts local-currency line amounts and a separate donor total, with `estimated_exchange_rate` computed correctly and `duration_months` passed through (chat); low local-currency confidence passed through unset (chat) and falls back to the org's own currency (budget); `create_budget_with_lines`'s curated tool-schema allowlist updated for the three new fields (mcp_bridge parity test)
- [x] 5.6 Bug found live-testing against a real donor template (`MamaCash Example- ApplicationBudgetSWV.xlsx`, added to `uploads/budget/`): its local-currency (AMD) column is itself a formula (`=eur_col*450`), so `filter_out_formula_rows` (1.2's fix) blanked it to `None` on every line — the AI then had only the EUR column's values to work with, silently mislabeling them as `local_currency` amounts (confirmed by `estimated_exchange_rate` computing to exactly 1.0). Fixed in `spreadsheet_reader.py`: `ExcelStructureDetector` now also loads the workbook with `data_only=True` and resolves a formula cell to its last-calculated cached value instead of blanking it, falling back to `None` only when no cached result exists. Added `TestFilterOutFormulaRowsWithCachedValue` in `test_spreadsheet_reader.py`. Side effect worth flagging: `compute_structure_fingerprint` hashes which columns are non-empty per row, so a formula-driven second-currency column now counts as non-empty where it previously didn't — any `DonorTemplateModel` saved before this fix from a formula-based dual-currency sheet won't fingerprint-match after it. No such templates exist yet (this change is unreleased), so no migration needed.
- [x] 5.7 Second live-testing finding on the same file: even on a cleanly-resolved, high-confidence line, the model was tucking the (now-redundant) donor-currency value into `extra_fields` (e.g. `{"costs_in_euro": 500}`) alongside a correctly-extracted local-currency `amount` — duplicating what the platform already derives via `estimated_exchange_rate`. Fixed at the code layer (not prompt-only, per the lesson from 5.6): chat's `_lines_from_extraction` (`import_excel.py`) now forces `extra_fields` to `None` for any line that clears the confidence threshold, regardless of what the model returned, so this is guaranteed rather than merely requested. Also tightened the `excel_budget_extraction` prompt itself (v3, migration `012_excel_extraction_prompt_v3_no_redundant_extra_fields`) to stop generating that redundant data in the first place — cost hygiene, not a correctness dependency. Deliberately deferred: when `local_currency` itself is low-confidence/unresolved at the sheet level, letting a user review and pick which column is real local currency — that's next-iteration UX work, not this pass. Added `test_high_confidence_line_drops_model_supplied_extra_fields`.
- [x] 5.8 Third live-testing finding on the same file: even with the Decision 9 pipeline fix (correct dual-value grid) and the Decision 10 extra_fields fix, the model still read the amount for `local_currency: "AMD"` off the EUR column (`estimated_exchange_rate: 1` recurred) — confirmed via a direct DB check that no stale `DonorTemplateModel` fingerprint match was involved, and via a direct grid dump that the input to the AI call was correct. Root cause: asking the model to pick a single `amount` by currency-role judgment is unreliable even when the mechanical parts (finding real numbers, reading header text) work. Fixed by no longer asking for that judgment: `ExcelExtractionLine` now reports `local_amount`/`target_amount` separately (schema + v4 prompt migration `013_excel_extraction_prompt_v4_local_and_target_amount`), and chat's `import_excel.py` deterministically swaps them per line when doing so makes their sums a better match against the sheet's own `donor_total_amount` — the one number in this pipeline that's read, not judged. `excel_import_structure.amount_col` is corrected the same way so a future template save doesn't bake in a swapped mapping. Added `_should_swap_local_and_target` with `test_swaps_local_and_target_when_model_mislabels_them`. Known residual gap noted in design.md Decision 11: doesn't help if the model collapses back to filling only one field.
- [x] 5.9b Fourth finding, this time from an `ai_audit_logs` inspection rather than a live-test screenshot: `prompt_version` always read `v1`. Root cause: the local `ai` DB's `alembic_version` was stuck at `010_seed_excel_extraction_prompt` — migrations 011-013 had never applied, so every one of 5.6-5.8's live-testing rounds actually ran against the original v1 prompt text (no dual-currency/formula/local-target guidance at all), despite the Python schema already requiring the newer fields. `alembic upgrade head` then failed outright with `StringDataRightTruncation`: migrations 011-013's revision ids (44-56 chars) exceed `alembic_version.version_num`'s `varchar(32)`, a limit every prior revision id in this service had implicitly respected. Also fixed `ai_audit_logs.prompt_version` being ambiguous against `parse_budget`'s/`decide_service`'s own version sequences in the same shared table — `excel_extraction_service.py` now writes `f"excel-extract {loaded_prompt.version}"`.
